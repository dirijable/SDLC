# ADR-002: Транзакционная защита часового слота

## Контекст и постановка задачи

REQ-FUNC-007 требует ровно одну успешную запись при двух конкурентных запросах. REQ-FUNC-016 запрещает блокировать слот с записью. Проверка только в интерфейсе не гарантирует результат при гонке.

## Драйверы решения

- Целостность пары «мастер — дата — час» важнее удобства повторной попытки.
- PostgreSQL уже обязателен по REQ-INT-004.
- Отменённые записи нужно сохранять как историю.
- Операции бронирования и блокировки должны быть согласованы.

## Рассмотренные варианты

1. Транзакция с блокировкой строки `WorkDay` и частичный уникальный индекс действующих записей.
2. Только проверка наличия записи перед `INSERT`.
3. Прикладная блокировка в памяти сервера.

## Итог решения

Выбран вариант 1. Бронирование и блокировка получают блокировку строки рабочего дня, повторно проверяют расписание, блоки и записи, затем сохраняют изменение. Частичный уникальный индекс по `(master_id, date, hour)` при `status=UPCOMING` защищает инвариант действующей записи даже при ошибке прикладного кода. Нарушение превращается в HTTP 409 с понятным сообщением.

### Последствия

- Транзакции конкурируют за один день мастера, поэтому их нужно делать короткими.
- Отменённая запись остаётся в истории и не мешает повторному бронированию.
- Блокировка и бронирование одного слота не могут оба завершиться успехом.

### Подтверждение

Интеграционный тест одновременно отправляет две брони одного слота и отдельно бронь с блокировкой. В каждом случае успешна одна операция; число действующих записей плюс блокировок для слота равно одному. После отмены проверяется повторное бронирование.

## Плюсы и минусы вариантов

| Вариант | Плюсы | Минусы |
|---|---|---|
| Транзакция + индекс | Работает между экземплярами сервера, сохраняет историю | Нужна миграция схемы и обработка конфликтов |
| Проверка перед INSERT | Проста | Два запроса могут пройти проверку одновременно |
| Блокировка в памяти | Не требует SQL-блокировки | Не работает при нескольких процессах и перезапуске |
